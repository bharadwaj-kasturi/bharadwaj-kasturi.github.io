Field notes

How each bug
works & where
to look for it

Short, vendor-neutral notes on the vulnerability classes above — what the flaw is, how it shows up in an application, and how it surfaces during testing. General methodology only; no target, no client, no live exploit.

AccessBroken Access Control & IDOR
The bugThe server trusts the client to decide what a user may see or do. A request references an object by identifier, and the app returns it without checking the caller actually owns it (IDOR), or exposes an action a lower-privileged role should never reach.
How it showsA profile page loads ?id=1052; changing it to 1051 returns someone else's record. Or an admin-only endpoint answers a normal user's request.
How to findMap every object reference and every privileged action, then replay each request as a different or lower-privileged account — swapping IDs, roles, and tenant scope — and watch for data or actions that should have been denied.
InjectionServer-Side Request Forgery (SSRF)
The bugThe server fetches a URL the user controls, so the user can make it request internal systems it can reach but the user cannot — cloud metadata endpoints, admin panels, or the loopback interface. Chained with a file scheme, it can read local files.
How it showsFeatures that take a URL: webhook setup, "import from link", PDF/thumbnail generators, avatar-by-URL. The server, not the browser, makes the outbound call.
How to findPoint every server-fetched URL at a collaborator host and confirm the callback originates from the server. Then probe internal targets and alternate schemes to gauge reach.
InjectionStored & Blind Cross-Site Scripting
The bugUser input is saved and later rendered into a page without being encoded, so injected script runs in another user's browser. "Blind" means it fires somewhere you can't see — an admin dashboard, a support console, a log viewer.
How it showsAny field that is stored and shown elsewhere: names, comments, file names, support tickets, user-agent logging.
How to findPlant a uniquely-tagged payload that calls back to a collaborator across every stored field, then wait — a callback reveals where it rendered, including back-office pages you never visit directly.
InjectionXSS via Prototype Pollution
The bugJavaScript that merges user input into objects without guarding __proto__ can alter the base prototype every object inherits from. A polluted property then flows into a sink — an HTML template, a config default — and becomes script execution.
How it showsClient-side apps with deep-merge, query-string parsers, or config libraries that copy untrusted keys into objects.
How to findSet a marker via crafted __proto__ keys in query or JSON input, confirm it lands on a fresh object, then trace whether any gadget in the app turns that property into a rendered sink.
LogicRace Conditions
The bugA check and the action it guards are not atomic. Fire many requests in the same instant and several slip through before the state updates — a one-time coupon redeemed repeatedly, a balance spent twice.
How it showsAnything with a "once" or "limit" rule: promo codes, withdrawals, invite acceptance, vote or rating caps.
How to findSend the same state-changing request in a tight parallel burst (single-packet timing) and check whether the limit held or the operation applied more times than allowed.
UploadUnrestricted File Upload & Arbitrary File Write
The bugAn upload trusts the client's stated type or name, letting a non-image land in a served directory, or a crafted path (../) write outside the intended folder — potentially overwriting existing files.
How it showsProfile pictures, document imports, bulk uploads — anywhere the file's name or content-type is taken at face value.
How to findVary extension, content-type, magic bytes, and traversal sequences in the filename; then confirm where the file lands and whether the server serves or executes it.
ExposureHardcoded Secrets in Client-Side Code
The bugKeys, tokens, or credentials shipped inside JavaScript or a mobile bundle. Anything the client holds is readable — "hidden" in minified code is not hidden.
How it showsAPI keys in bundles, secrets in source maps, admin tokens in comments, third-party credentials embedded for convenience.
How to findPull every script and mobile artifact, unminify, and pattern-scan for key formats and entropy; then verify each candidate is live and check what it authorizes.
LogicBusiness Logic & Insecure Design
The bugEvery request is individually valid, but the intended workflow can be bent — steps skipped, reordered, or repeated — to reach a state the designer never allowed. No payload; the logic itself is the flaw.
How it showsMulti-step flows: checkout, refunds, tiered pricing, approval chains, quota and entitlement enforcement.
How to findModel the intended flow, then deliberately break its assumptions — negative quantities, skipped verification, replayed confirmations, tampered client-trusted totals — and see what the server still accepts.
AIPrompt Injection in AI-Assisted Features
The bugAn LLM feature mixes trusted instructions with untrusted content in the same context. Attacker-controlled text instructs the model to ignore its rules, leak its context, or misuse a connected tool — including data reached through the model's own permissions.
How it showsChat assistants, summarizers, and agents that read user documents, tickets, or web pages and can call tools or query data on the user's behalf.
How to findFeed instructions through every channel the model ingests — direct prompts and indirect content it reads — and test whether it overrides guardrails, discloses system context, or performs actions beyond the user's own entitlements.
ConfigCORS Misconfiguration
The bugThe server reflects or over-trusts the request Origin and returns Access-Control-Allow-Credentials: true, letting a malicious site read authenticated responses on a victim's behalf.
How it showsAPIs that echo the Origin header back into Access-Control-Allow-Origin, or trust null and arbitrary subdomains.
How to findSend requests with unexpected Origin values and inspect the CORS response headers; a reflected origin paired with credentialed access confirms cross-origin data reads are possible.
ControlMissing Rate Limiting
The bugNo throttle on sensitive actions, so requests can be repeated at will — enabling credential brute force, OTP guessing, coupon abuse, or enumeration.
How it showsLogin, forgot-password, OTP verification, and search or lookup endpoints that answer unlimited attempts.
How to findAutomate a controlled volume of requests against the action and confirm none are throttled, challenged, or locked — while watching for rate limits keyed weakly enough to bypass by rotating a header.
SessionImproper Session Invalidation
The bugA session token stays valid after it should have died — after logout, password change, or account deactivation — so a captured token keeps working.
How it showsLogout that only clears the client; password resets that don't revoke other sessions; disabled accounts whose old tokens still authenticate.
How to findCapture a valid token, trigger the event that should end it, then replay the token and confirm whether the server still honors it.

Walkthroughs

Step-by-step,
illustrated on a
synthetic app

Detailed reproduction flow for a handful of the classes above, illustrated on a demo application I built for teaching — demo.shopline.test. Every screen, URL, name, and value shown is invented for illustration.

No client, no real system, no engagement data appears here. The mockups are hand-drawn UI, not screenshots — nothing to blur, because nothing is real.

AccessIDOR — reading another user's order

On the demo store, each customer can open their own order receipt. The receipt is fetched by a numeric id in the URL — and the server never checks that the order belongs to the logged-in user. That missing ownership check is the whole bug.

  1. Open your own order and note the pattern

    Logged in as ava@example.test, you view your receipt. The identifier sits in plain sight in the address bar — sequential, guessable.

  2. Decrement the identifier

    Change id=1042 to id=1041 and re-send. If the server enforced ownership it would answer 403 Forbidden. Here it returns 200 with someone else's receipt.

  3. Confirm it is another account, then measure the range

    The returned name and email are not yours — that confirms the finding. Walking the id up and down maps how many records are reachable. For the report you would stop at proof and record the impact, never harvest live data.

Fix —enforce object ownership server-side — the record's owner must equal the authenticated user before it is returned.

InjectionSSRF — reaching an internal endpoint

The demo store lets a merchant register a webhook URL for order events. The server fetches that URL — so if it doesn't restrict the destination, it can be steered at systems only the server can reach.

  1. Find the feature that fetches a URL for you

    Merchant settings accept a callback address. The browser never loads it — the server does, from inside the network.

  2. Point it at a listener you control

    Set the URL to an out-of-band collaborator host and trigger the event. A callback from the server's IP proves the server makes the request — the precondition for SSRF.

  3. Probe internal-only destinations

    Now aim at addresses the server can reach but you cannot — cloud metadata or loopback services. A useful response where the internet would time out demonstrates internal reach. Scope and rules of engagement bound how far this goes.

Fix —allow-list destinations, resolve-then-validate against internal ranges, and block redirects to private addresses.

InjectionBlind stored XSS — firing in an admin panel

A shopper can set a display name. Staff later see that name in a back-office console. If the name is stored raw and rendered without encoding, the shopper's markup runs in the staff member's browser — somewhere the shopper can't see.

  1. Plant a tagged, call-home payload

    In the display-name field, submit a script that loads a uniquely-tagged resource from a collaborator, so a hit tells you exactly which sink rendered it.

  2. Wait for it to render somewhere you can't reach

    You never load the admin console — but when staff open the customer list, the stored name executes in their session and the tagged resource is requested.

  3. Confirm from the callback

    The collaborator logs the tagged hit — proof the payload stored and executed in a privileged context. A real report stops at that proof of execution; it does not pivot into staff accounts.

Fix —context-aware output encoding at every sink, plus a strict Content-Security-Policy as defence in depth.

LogicRace condition — redeeming a one-time coupon twice

A coupon is meant to work once. The code checks "is it unused?" and then marks it used — but those are two separate steps. Fire many redemptions in the same instant and several pass the check before any of them flips the flag.

  1. Establish the single-use rule

    Redeem the coupon once, normally. A second attempt is rejected — the intended behaviour.

  2. Send many redemptions simultaneously

    With a fresh coupon, dispatch a tight parallel burst (single-packet timing) so they all arrive during the same check-then-update window.

  3. Observe the limit breached

    Instead of one success, several apply — the discount stacks well past "once", proving the check and the update were not atomic.

Fix —make check-and-consume atomic — a single conditional update, a row lock, or a unique constraint on redemption.

UploadUnrestricted upload — content-type trust bypass

The avatar upload says "images only", but it decides by trusting the browser-supplied Content-Type and the file extension — both of which the client fully controls. Trusting client-declared type is the flaw.

  1. Baseline a normal upload

    A real PNG uploads fine and is served back from a predictable path.

  2. Send a non-image but declare it an image

    Upload a different file type while keeping Content-Type: image/png and an image-looking name. If validation only reads those, it accepts the file.

  3. Confirm where it lands and how it's served

    Retrieve the stored file and check the response — is it served inside the web root, with what type and headers? That determines the real impact, which you then document for the fix.

Fix —validate real content (magic bytes), re-encode images, store outside the web root, and serve with a fixed safe type.
